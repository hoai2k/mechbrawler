# JJK Brawler II — 2.5D reimplementation plan

The goal: keep the game — menus, backgrounds, controls, kits, feel — and replace
the presentation. Fighters become rigged 3D models rendered in a 2D anime style
(the Guilty Gear Xrd / Smash Bros approach), viewed through a Smash-style
perspective camera. Gameplay stays on the 2D plane it has always been on.

## Why this is tractable here

The codebase already has the one property this migration lives or dies on:
**the simulation never touches the renderer.** `fighter.js`, `combat.js`,
`moves.js` and friends run a fixed-timestep 60 Hz sim in a flat 1280×720 world;
`render.js`/`sprites.js` read fighter state (`animState`, position, facing,
timers) and draw it. Smash itself is exactly this shape — 2D gameplay, 3D
presentation. So:

- **Nothing in the sim changes.** Hitboxes, hurtboxes, physics, kits, AI,
  blast zones, stages-as-platform-lists: all untouched. `docs/hitbox-audit.md`
  stays true.
- **Menus and HUD are DOM/CSS** (`ui.js`, `styles.css`, `index.html`) —
  untouched.
- **Controls** (`input.js`) — untouched.
- **Backgrounds** — the existing painted backgrounds stay, promoted to
  parallax-layered textured planes behind the 3D stage.
- What changes is one seam: the draw path, plus a new asset class (rigged
  `.glb` models) fed by a pipeline that mirrors the existing sprite
  request/intake/workbench workflow.

## Architecture

### Rendering: three.js under the existing 2D canvas

Add **three.js as the single new dependency**, vendored as an ES module (or via
an import map) so the no-build-step constraint holds. Rendering becomes two
stacked canvases:

1. **WebGL canvas (bottom)** — the 3D scene: stage, fighters, eventually FX.
2. **Existing 2D canvas (top, alpha)** — everything not yet ported keeps
   drawing exactly as today: particles, strike arcs, popups, banners, domain
   overlays, debug hitboxes. These migrate to the 3D scene gradually (or never,
   for screen-space things like banners).

A small renderer facade (`src/render3d/`) owns the scene and exposes the same
call the loop makes today (`draw(state)`), plus `worldToScreen(x, y)` so the
2D overlay canvas and DOM HUD can keep positioning things in sim coordinates.

### Coordinate mapping

Sim space stays authoritative. One linear mapping into the 3D world:

- `worldX = (x - 640) * S`, `worldY = -(y - GROUND) * S`, fighters on `z = 0`.
- Platforms are shallow extruded boxes straddling `z = 0` (visual depth only —
  collision is still the sim's 2D rects).
- Background art on large planes at negative z in 2–3 parallax layers; a far
  skydome/plane keeps the camera dolly from ever seeing an edge.

### Camera (the Smash camera)

Replace `camera.js`'s pan/zoom with a **perspective camera on a dolly**:

- Long lens (FOV ~30°) so fighters at different x barely distort — this is
  what makes Smash read as "2D with depth."
- Target = midpoint of alive fighters (same math as today); **distance**
  replaces zoom, driven by fighter spread with the same clamped-lerp smoothing.
- Subtle lateral offset and yaw (a few degrees) as the fighters move, so the
  parallax and platform sides are always slightly visible — this is the whole
  2.5D effect.
- `cam.shake` → positional noise; `cam.kick` → short FOV/dolly punch-in.
- Drama hooks: ult/domain activations get authored camera moves (fast dolly-in,
  slight dutch tilt, per-domain background swap already exists in the sim).
- Keep the sim's blast zones and world clamp logic reading the same numbers;
  only presentation moves.

### Anime rendering style (the Xrd recipe)

- **Toon shading**: 2-band ramp lighting (three's `MeshToonMaterial` with a
  custom gradient map, upgraded later to a small custom shader), one
  directional key light per stage, shadow color tinted from the stage's
  existing `tint`.
- **Outlines**: inverted-hull back-face shells, thickness scaled by camera
  distance. Interior lines painted into textures (cheaper and more "drawn"
  than edge-detection post).
- **Palette fidelity**: character textures use flat fills sampled from the
  existing sprites' palettes — the roster keeps its exact colors.
- **Animation on twos**: sample skeletal animation at 12–15 fps (hold poses
  between samples) while the camera and motion trails stay at 60. This single
  trick is most of why Xrd reads as 2D animation, and it happens to match the
  low-frame-count feel the sprite game already has.
- Rim light + the existing `motion.js` squash/lean/tumble applied as root-bone
  transforms, so the current game feel (dash lean, tumble spin, hit squash)
  carries straight over.

### Animation system

The existing anim state machine is the contract. `DEFAULT_ANIMS` /
`SEMANTIC_ANIMS` define ~25 states (idle, run, dash, jump, fall, land, hurt,
crouch, crouch attack, shield, ledge, dodge roll/air, light, air light,
side/up/down heavy, charge, three specials, ult, dizzy, prone, win). The 3D
layer maps `fighter.animState + timeInState` → an animation clip, exactly as
`sprites.js` maps it to frames today — so **hitbox timing never desyncs from
art**, because the sim's timers stay the clock.

Two tiers, shipped in order:

1. **Pose-hold tier** (gets the whole roster in 3D fast): each state is a
   1–2 keyframe pose clip authored to match the character's existing sprite
   poses, crossfaded over ~60 ms, with `motion.js` doing the life. This is a
   direct translation of what the sprite game shows today.
2. **Full-motion tier**: real keyframed clips (Mixamo/retargeted locomotion +
   hand-keyed attacks), rolled out per character in rounds, exactly like
   sprite art rounds.

### Character model pipeline (sprites as seed material)

New asset class: `assets/models/<char>/<char>.glb` — rigged, with a **shared
humanoid skeleton** (Mixamo-compatible bone names) for the ~26 humanoids so
clips retarget across the roster; bespoke rigs for the non-humanoids (panda,
mahoraga, kurourushi, mechamaru, the curses).

Pipeline, mirroring the sprite workflow the repo already runs:

1. **Seed sheets** — new tool `tools/build_model_reference.py`: for each
   character, composite a reference board from existing sprites (idle front,
   run, key attack silhouettes) plus the extracted palette and the height from
   `docs/character-heights.md`. This is the "source material" handed to
   whatever generates the model.
2. **Generation** — recommended route: AI image-to-3D (Meshy / Tripo /
   Hunyuan3D-class tools) seeded with the reference board, then auto-rig
   (Mixamo or built-in), then a cleanup pass (retopo if needed, toon-texture
   repaint with the flat palette). Hand-modeling in Blender from the same
   boards is the fallback for characters the generators mangle. Either way the
   deliverable is the same `.glb`, so routes can mix per character.
3. **Validation** — `tools/check_models.mjs` (node + three, headless): loads
   each `.glb`, asserts bone names, unit height vs `heights.js`, required clip
   list, triangle budget (≤ ~15k), texture size. The moral equivalent of
   `check_kits.mjs`.
4. **Review** — extend the workbench with a model tab: orbit viewer, play each
   state's clip beside the character's sprite for that state, and the same
   flag/note/variant machinery (`needsReplacement` / `wantsImprovement`)
   already built for sprites. `docs/model-requests.md` joins the request-round
   docs.

Scale is calibrated so the model's rendered silhouette height matches what
`silhouette.js` measured from the sprites — hurtboxes are derived from those
measurements, so fighters stay exactly as hittable as they are today.

### What stays 2D (deliberately)

- **Menus, character select, HUD** — DOM, untouched.
- **Banners/popups** — screen-space, on the overlay canvas.
- **Backgrounds** — existing paintings, as parallax planes.
- **Particles & stage FX** — start on the overlay canvas verbatim; migrate the
  ones that need depth (projectiles, summons, domain effects) to billboarded
  quads/shader trails in the scene over time. Summons can ship as billboards of
  their existing sprites indefinitely — Smash does exactly this for assist
  characters' effects.

## Phased migration (playable at every step)

**Phase 0 — 2.5D camera with zero new art.** Vendor three.js, stack the
canvases, build the coordinate mapping and Smash camera, and render fighters as
**billboarded quads textured with their existing sprites**, platforms as
extruded boxes, backgrounds as parallax planes. This ships the entire 2.5D
camera system and proves the seam while every character still uses today's
art. (Also permanently useful: it's the fallback path for un-migrated
characters.)

**Phase 1 — Stage look.** Toon materials + outlines on platforms, stage light
rigs keyed to each stage's palette/tint, camera drama hooks (ult dolly, KO
punch).

**Phase 2 — Vertical slice: one character in 3D.** Gojo or Yuji: model through
the full pipeline, toon shader + outlines, pose-hold clips for all ~25 states.
Mixed roster is a hard requirement — a 3D fighter beside billboard fighters —
because the roster will migrate character-by-character for a long time.

**Phase 3 — Slice to full motion.** Real locomotion/attack clips for the slice
character; animation-on-twos tuning; motion-trail port; sign-off on "does this
read as the anime."

**Phase 4 — Roster rounds.** Model request rounds through the
pipeline+workbench, a few characters per round, humanoids first (shared rig
amortizes everything), bespoke rigs last. Sprite billboards cover everyone not
yet delivered.

**Phase 5 — FX migration.** Projectiles/summons to billboards in-scene,
strike arcs to shader trails, domain overlays to fullscreen shader passes.

**Phase 6 — Retire or keep.** Either cut the sprite fighter path, or keep it
behind a "Classic" toggle — it's nearly free to keep since Phase 0's billboard
renderer is the compatibility path anyway.

## Risks and mitigations

- **Generated model quality** — the same risk sprite rounds already manage;
  the flag/variant/re-request loop is built. Non-humanoids are the hard 20%:
  schedule them last, accept billboards for them for a long while.
- **Performance** — inverted-hull outlines double fighter draw calls; at ≤4
  fighters, low-poly models and one light this is comfortably 60 fps on
  integrated GPUs. Budget enforced by `check_models.mjs`.
- **No-build-step constraint** — three.js ships an official ES module build;
  vendor it (or import-map it). No bundler needed.
- **Feel regression** — the sim is untouched, so feel risk is purely visual
  timing; the anim layer reads the sim's own timers, and the workbench
  side-by-side (sprite vs model per state) is the review gate.
- **Asset size** — models are a few MB per character vs ~40 MB of sprites;
  the background-streaming loader in `assets.js` extends to `.glb`s trivially.

## Recommended decisions (defaults, changeable)

- **Engine**: three.js (vendored ESM). Babylon is heavier; raw WebGL is a
  time sink with no upside here.
- **Model source**: AI image-to-3D seeded from sprite reference boards, with
  Blender cleanup — matches the existing "request round" workflow best.
- **Rig**: shared Mixamo-compatible humanoid skeleton; bespoke only where the
  body demands it.
- **Classic mode**: keep the sprite billboard path as a toggle.
