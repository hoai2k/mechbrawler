# 2.5D Camera — implementation plan & status

A Smash-style perspective camera for the existing 2D game, enabled with
`?camera=3d` and off by default (no param = today's renderer, unchanged).
No new art, no sim changes: fighters stay their current sprites,
billboarded into a real 3D scene, and every platform, hitbox and blast
zone keeps its exact 2D behavior.

## Status

**All eight steps of the implementation order are built and
smoke-tested.** The mode is feature-complete against this plan; what
remains is optional per-board polish, listed under "Still open" below.
Deviations from the original plan are called out inline as **[built]**
notes.

| step | state |
|---|---|
| 1. Scaffold (param, lazy import, glCanvas, vendored three.js, fallback) | ✅ done |
| 2. Static scene (mapping, platforms, background plane) | ✅ done |
| 3. Billboards (fighters, projectiles) | ✅ done |
| 4. Rig (framing/dolly/yaw/lookahead/shake/kick) | ✅ done |
| 5. Overlay projection | ✅ done |
| 6. Drama hooks (intro, ult, domain, GAME) | ✅ done |
| 7. Board personalities + cues | ✅ done — all 20 boards wired |
| 8. Garnish cards | ✅ done — 5 boards; the rest are open polish |

Verification: `tools/smoke_camera.mjs` (headless rig invariants),
`tools/smoke_camera3d.mjs` (in-browser: the mode takes, the scene draws,
garnish spawns and clears), `tools/smoke_render_backend.mjs` and
`tools/smoke_stages.mjs` (flat mode untouched), plus screenshots of each
garnish board and of debug hitboxes landing on the billboards.

Known, deliberate gaps in 3d mode:

- **Glow halos** (canvas `shadowBlur` on fighters) have no cheap GL
  equivalent and are skipped on billboards; strike arcs and particles
  still draw on the overlay and carry the energy read.
- **Missing-art placeholder** boxes draw only in flat mode; in 3d a
  failed sprite logs the existing console warning.
- **Projectile comet trails** stay on the overlay canvas (additive
  strokes); only the projectile body is a scene quad.
- **Summons and installs are always cards.** A transformed fighter
  (Megumi as Mahoraga) draws from the install's own still art in every
  mode, and brawler summons take the sprite-card path, so `?render=3d`
  shows a modelled fighter beside a card-drawn summon. Correct for now —
  summons have no rigs — and the seam is per character, so it resolves
  itself as rigs land.

Still open, all optional polish rather than missing pieces:

- **Garnish for the remaining boards.** Five have cards (below); the
  other fifteen run on camera personality and cues alone. Each is an
  independent commit against a system that already exists.
- **[delivered] Higher-resolution backdrops.** The one measured art change
  that would pay for itself — see §10. Commissioned as **18E**, with the
  near-field cards it argues for as **18F**, and both are now in the game:
  twenty backdrops at 3200×1800 and all fourteen cards, so every procedural
  stand-in in `garnish.js` is a painting. See
  [the history](asset-requests-history.md#round-18--delivered).
- **A Settings toggle** that writes `?camera=3d` and reloads (§1).

**[built] The render backends now compose natively with this camera.** Each
one declares how it presents as geometry — sprites and billboards as cards,
`?render=3d` as the real rig in this scene — see **§11**.

**Withdrawn:** the second blurred parallax backdrop layer at `z = -22`
that §3 originally proposed. Measured, it buys 2.3 px of differential
shift at the yaw this camera actually reaches, and it is the same image
twice, which reads as a smear rather than as depth. §10 has the numbers.

## 1. Mode selection

```js
// main.js init(): lazy import, double-guarded
if (params.get("camera") === "3d") { const mod = await import("./camera3d/index.js"); ... }
```

- `flat` is the default and the fallback. If WebGL context creation fails,
  log a console warning and run flat — never a broken screen.
- The 3D module is lazy-imported only when the param is set, so the flat
  path pays zero bytes and zero startup cost. three.js is only fetched in
  3d mode; the default game keeps its no-build-step, no-dependency
  property.
- **[built]** The mode gate lives in `src/camera_mode.js` — a tiny,
  three.js-free module both sides import — rather than an export from
  main.js (which render.js could not import without a cycle). It also
  carries `cameraCue()`, the feature-detected hook stage gimmicks poke.
- Later a Settings toggle can write the param and reload; the param stays
  the source of truth so a URL fully describes what a player sees.

## 2. Architecture: two stacked canvases

```
<canvas id="glCanvas">    ← NEW, z-index below, WebGL (three.js, vendored ESM)
<canvas id="gameCanvas">  ← existing, alpha, on top
```

In `3d` mode the scene (backdrop, domain planes, platforms, fighters,
projectiles) renders on `glCanvas`, and `render.js` skips its own versions
of those — but keeps drawing everything else exactly as today on the
transparent top canvas: particles, strike arcs, popups, banners, domain
overlays, vignette, flash, debug hitboxes, fighter adornments (shield
bubbles, meters, status effects, revival platforms).

**What moved into the scene, and why.** Everything on the overlay is *in front
of* the fighters by construction, because the overlay canvas is above the GL
layer. That is right for a shield bubble or a damage popup and wrong for
anything the flat renderer deliberately draws UNDER a body — and three things
were in that second group:

| | flat | was, in 2.5D | now |
|---|---|---|---|
| install aura | under the body | overlay, in front | quad in the scene |
| projectile art | before `drawFighters` | quad, but painted after them | quad, behind them |
| `state.entities` `draw` | before `drawFighters` | overlay, in front | one quad in the scene |

The projectile one is the smallest change and the loudest symptom: Gakuganji's
Power Chord is 120 px of opaque energy art, and parked on the fighter it was
about to hit it erased them from the chest down. The entity layer was worse
still — an Encore wave is 300 px, and it took out the fighter across the stage
as well.

**The install aura**, whose whole job flat is to sit under the body
(`render.js` paints it between the shadow and the body), lit the fighter from
in front like frosted glass while it was on the overlay. It is now
a quad drawn by `billboards.js` in the same paint order, and it is the one
quad in this scene with `depthTest: true`: under `?render=3d` the body is
opaque geometry, and three.js draws every transparent quad after every
opaque mesh whatever its `renderOrder`, so only the depth buffer can put
the aura behind a rig. Art auras replay `drawInstallAura`'s transform chain
(the tilt turns about the feet); the procedural ellipse and Distortion
Solo's clipped ring are baked into a per-fighter canvas by `render.js`'s
own `paintProceduralAura`, so there is one drawing, not two. Guarded by
`tools/smoke_camera3d.mjs` ("the install aura is drawn in the scene").

**The entity layer** could not take the same treatment one effect at a time:
`state.entities` are drawing CODE, not pictures — dozens of them, each painting
arbitrary canvas 2D in sim coordinates. So the whole layer becomes one picture.
`src/camera3d/effects.js` renders every `e.draw` into an offscreen canvas
covering the sim rectangle the camera can currently see (the overlay affine,
inverted, then squared to the canvas aspect so the scale is uniform), and that
canvas goes in as a single quad on z = 0 behind the fighters. Draw order is
restored for every effect at once, with no per-effect work and nothing changed
in flat mode. It costs one canvas repaint and one texture upload per frame, and
only when there is an entity on screen at all — no effects, no layer. `e.drawTop`
still runs on the overlay, because effects that mean to cover the fighters are
exactly what that hook is for. Guarded by `tools/smoke_camera3d.mjs` ("entity
effects are drawn into the scene").

Files, all as planned:

| file | owns |
|---|---|
| `src/camera3d/index.js` | scene setup, draw entry point, resize, mode fallback |
| `src/camera3d/rig.js` | the camera rig (§4) + the overlay projection (§5) |
| `src/camera3d/billboards.js` | fighter/projectile quads, texture cache |
| `src/camera3d/effects.js` | **[built]** the `state.entities` draw layer, as one quad |
| `src/camera3d/quads.js` | **[built]** shared quad placement, pooling, draw order |
| `src/camera3d/garnish.js` | **[built]** per-board cards off the gameplay plane (§7c) |
| `src/camera3d/stage_geo.js` | extruded platforms, background/tint/domain planes |
| `src/config_camera.js` | every dial, comment-per-dial |
| `src/camera_mode.js` | **[built]** the mode gate + cue seam (see §1) |

**[built] `src/camera3d/`, NOT `render3d/`.** The repo has a root-level
`render3d/` that is a *character render backend* — the same fighters drawn
as live toon-shaded models, picked with `?render=3d`. That is an
orthogonal choice to this one: `render3d/` changes **how a character
becomes pixels**, `src/camera3d/` changes **the stage and lens they exist
in**, and the two compose (`?render=3d&camera=3d` is legitimate). Two
directories called `render3d` meaning different things would have been a
permanent tax on reading this repo.

three.js is vendored at `vendor/three/` — official ESM build, no bundler.
**[built]** It is *shared* with both model backends rather than
duplicated. Two copies would not merely waste the bytes: the modes
compose, so both can be live at once, and two engines have mutually
unrecognisable classes — which fails as objects silently not rendering
rather than as an error. See `vendor/three/VENDOR.md`.

## 3. Coordinate mapping

Sim space stays authoritative; the scene is a linear image of it.

```
S = 1/100                            // 100 sim px = 1 world unit
worldX = (x - 640) * S               // stage center at origin
worldY = (568 - y) * S               // +Y up; 568 = typical main-platform top
z = 0                                // the gameplay plane
```

- **Fighters / projectiles**: textured quads on `z = 0`.
  **[built]** Parity with the flat renderer is *by construction*: the
  quad's matrix is composed by replaying `drawCharFrame`'s exact canvas
  transform chain (translate, squash about `com`, rotate about `com`,
  mirror, image rect) in sim coordinates, inside a group whose transform
  is the mapping above. `frameMeta` placement, `currentFrame` pose and
  `motion.js` transforms are the same data the flat path reads.
  Afterimage trails ride the same quad builder.
- **Platforms**: boxes extruded `depth = 1.4` world units (main) / `0.9`
  (side/top), extruded *away* from the camera so the face stays on the
  gameplay plane. **[built]** The face of each box is painted by
  `drawPlatformShape` itself into a canvas texture — pixel-identical to
  flat mode — with lit top faces and dark sides; ghost/crumble/accent
  states re-key the texture and hide the solid faces.
- **Background**: the stage painting on a plane at `z = -14`, over-filling
  the frustum at max dolly-out. Stage `tint` and the flat renderer's
  darkening wash are translucent planes at `z = -6`; the domain
  expansion's dim + art + grade live at `z = -5`, behind the platforms
  and in front of the backdrop — the flat renderer's exact layering.
  The second blurred parallax copy this section originally proposed was
  measured and withdrawn — see §10.

## 4. The camera rig

A perspective camera on a dolly, replacing pan/zoom while **reusing
`camera.js`'s existing targeting math** — `updateCamera()` runs unmodified
in both modes; the rig is a consumer of `state.camera`, never a
replacement.

**Lens.** `fov = 30°` vertical, near 0.1, far 60.

**Framing.** From the sim's zoom: `D = (720/zoom) * S / (2 tan(fov/2))`
≈ 13.4 world units at zoom 1. Position `(camX, camY + heightBias, D)`,
`heightBias +0.4`, `pitch -2°`.

**Yaw.** `clamp(camX * 0.9°/unit, ±4°)`, smoothed. Fights near a ledge
show that ledge's platform side-face; center stage is nearly head-on.

**Lookahead.** LookAt leads average alive-fighter vx,
`clamp(avgVx * 0.06, ±0.5)` world units.

**Shake / kick.** `cam.shake` → positional noise, world-scaled;
`cam.kick` → FOV punch `30° → 27.5°` over 60 ms, back over 180 ms —
every existing `cam.kick` call site inherits it.

**Drama hooks** (existing sim state only; `introT`/`endT` are now
mirrored onto `state` by main.js for the rig to read):

- **Ult cast** (`action.kind === "ult"`): dolly to 0.8×D on the caster,
  ±2.5° dutch, ease back.
- **Domain cast**: same arrival, then a slow 8 s drift-out while the
  domain overlay owns the screen.
- **GAME** (`endT > 0`): dolly to 0.7×D on the winner, yaw easing to 0.
- **Round intro** (`introT > 0`): start at 1.25×D with +6° yaw, ease in
  as READY…/GO! plays.
- **Respawn**: no special move (normal framing already includes the
  revival platform).

All constants in `config_camera.js`.

## 5. The overlay projection

Everything still drawn on the 2D canvas positions itself in sim
coordinates. In 3d mode `render.js` replaces `applyCamera`'s transform
with the affine fitted to the projection of the gameplay plane
(`rig.overlayTransform()`), so particles, popups, strike arcs and hitbox
debug land on the fighters with zero per-effect changes.
`rig.worldToScreen(x, y)` is exported for anything DOM-positioned.

**[built]** One refinement over the plan: the projection of the tilted
plane is a homography, not an affine — pitch + heightBias give it a ~1%
per-100-px scale gradient. The fit is therefore **pinned at the mean
alive-fighter position** (tangent there, wide-secant slopes): sub-pixel
exactly where hitboxes, particles and popups must coincide with the
billboards, with the residual pushed to empty frame corners
(`smoke_camera.mjs` asserts the tolerances).

## 6. Draw flow in 3d mode

As planned (§6 of the original): `draw()` branches once at the top;
`draw3d()` renders the scene, then replays the overlay list with the
projected transform, then the screen-space draws, unchanged.

**(c) Garnish cards** (`src/camera3d/garnish.js`) — flat textured quads
OFF the gameplay plane, which is the one thing the flat renderer cannot

effects in stage_fx.js; no new art.

| Board | Cards |
|---|---|
| **Crosswalk Rush** | Vehicle silhouettes at `z ≈ +2`, spawned by the *same* `surge` cue that launches the hazard's cars, sweeping in front of the whole fight |
| **Lantern Corridor** | Paper lanterns at `z ≈ +2` hanging into the top of frame, drifting past the lens |
| **Training Bridge** | Falling leaves across `z = +0.9…+4.2`, near ones bigger, faster and fainter |
| **Empty City** | Rubble tumbling toward the lens on the `rattle` cue as a roof gives way |
| **Billboard Roof** | Hoardings on gantries at `z ≈ −4`, behind the stage, blown out by the `lightning` cue |

Two rules keep it garnish rather than clutter, and both are load-bearing:
**nothing here touches the simulation** (no card has a hitbox or is
visible to the AI), and **readability wins** — anything crossing in front
of the fighters is fast and just under opaque, or it is confined to a
band the fight does not occupy. Lanterns hang in the rafters; traffic
crosses the legs and clears in under a second.

`GARNISH` in `config_camera.js` is the switch: `enabled` (default `true`)
turns every card off everywhere while leaving the rest of the mode — the
scene, the rig, the drama shots, the per-board cues — running untouched,
and `interval` scales how often the ambient systems spawn. Turning it off
clears the sky already up rather than merely stopping new spawns, and
turning it back on restores standing scenery without needing a fresh
match; `smoke_camera3d.mjs` asserts both directions. It has its own
switch because garnish is the only part of this mode that deliberately
puts things *between* the lens and the fight — the first thing to reach
for if a board reads as too busy.

**[built]** Two implementation notes worth keeping:

- A card at `z ≠ 0` does **not** land where the same sim `y` lands at
  `z = 0`. It is nearer the camera, so the rig's small downward pitch
  throws it further from the centre of frame and magnifies it. Foreground
  cards are therefore authored well above where they should appear.
- Placement, pooling and draw order are shared with the fighter
  billboards through `src/camera3d/quads.js`, which also holds the
  `ORDER` table. Layering in a scene that mixes transparent quads with
  opaque boxes is stated there rather than left to three.js's sort.

## 8. Testing & performance

Two smoke tests, split along what each can actually reach:

- **`tools/smoke_camera.mjs`** runs the real `updateCamera()` + rig
  headless against scripted fighter paths and asserts framing invariants
  — fighters inside the frame with margin, dolly inside clamps,
  yaw/roll/fov bounded, no NaNs across KO/respawn/ult/domain/GAME/cue
  storms, and the overlay affine within tolerance of the true
  projection. No browser, no WebGL, so it is fast enough to run on every
  change.
- **`tools/smoke_camera3d.mjs`** covers everything that needs a real
  context — the scene, the platform boxes, the billboard quads and the
  garnish, whose textures need a canvas 2D context Node does not have.
  It is built around the QUIET failure: a 3D scene that renders nothing
  throws no errors and looks exactly like the intended flat fallback. So
  it asserts the mode did not fall back, that a quad was drawn per
  fighter, that garnish spawned on the boards that have it, and that it
  is cleared when the board changes. `debugStats()` in
  `camera3d/index.js` exists for this and nothing else.
- **Parity**: debug hitboxes (`Backquote`) over the billboards are the
  in-browser acceptance test; verified by screenshot.
- **Budget**: a dozen boxes, ~10 quads, a few planes, no lights
  (MeshBasicMaterial throughout) — trivially 60 fps on integrated GPUs.
  Billboard textures are uploaded per frame-image on first use and
  cached; they reuse the already-loaded sprite images.
- **Resize/DPR**: `camera3d.resize()` mirrors `resizeCanvas()`
  (`setSize`, `setPixelRatio(min(dpr, 2))`), aspect fixed by the same
  CSS letterbox.

## 9. Out of scope (deliberately)

3D character models, toon shading, porting particles/FX into the scene,
menu/HUD changes, any sim change. The `?render=billboard` backend
(per-character 3D models, `billboards/`) is a separate seam and composes
with this camera: that backend changes *how a character becomes pixels*,
this mode changes *the stage and lens they exist in*.

## 10. Would different background art help? (measured)

Asked after the mode shipped, and worth writing down because the intuitive
answer — "cut the paintings into parallax layers" — turns out to be the
wrong one. Numbers from `dollyFor()` and the real config; reproduce them
by projecting a point at depth `d` behind the gameplay plane at yaw `t`:
`x = f·d·sin t / (D + d·cos t)`, with `f = 0.5/tan(fov/2)` and `D ≈ 13.4`.

**1. This camera barely moves sideways.** `camera.js` clamps `cam.x` to
`[640/zoom, 1280 − 640/zoom]`, so at zoom 1.0 it is pinned at exactly 640
and the yaw is *exactly zero*. Only at full zoom-in (1.18, fighters close
together) does `cam.x` get ±98 px of travel — **yaw ±0.88°**. The ±4° the
rig clamps to is only ever reached in the drama shots, where the focus
blend pulls the camera onto one fighter. That single fact decides
everything below.

**2. So backdrop parallax layers are not worth an art round.** Splitting
the painting between `z = −14` and `z = −22` buys **2.3 px** of
differential shift in normal play, **10.4 px** in a drama shot. Against
the cost of re-cutting twenty paintings into registered layers with
alpha, that is not a trade worth making. (This is why the blurred-copy
idea in §3 is withdrawn: 2.3 px, and doubling one image reads as a smear.)

**3. The depth cue that already works is the dolly, not the yaw.** Zooming
from 1.0 to 1.18 grows the gameplay plane 18% while the backdrop grows
8% and a `z = −22` layer would grow 6%. That differential *is* parallax,
it needs no camera translation, and one flat plane already delivers it.

**4. Lateral parallax lives in the near field, which is garnish, not
backdrop.** A card at `z = +2` against the backdrop is **14 px** apart at
0.88° and **64 px** at 4° — six times what splitting the backdrop buys,
because the term that matters is proximity to the lens. The system for
this already exists (§7c) and currently draws procedurally.

**5. The one change that would measurably pay off is resolution.** The
backdrop plane over-fills the frustum (×1.5 height, ×1.35 width) so that
no dolly or yaw can ever reveal an edge. The cost is that only **49.4%**
of the image's linear extent is ever on screen: a 1600×900 painting puts
**790 source pixels across 1280 CSS pixels — a 1.62× upscale, 3.24× at
DPR 2**, where flat mode shows the whole image at a slight *down*scale.
That softness is the most visible art deficit in 3d mode.

    for parity with flat mode:  ~3240 px wide  (≈ 3200×1800)

**This has been delivered** — 18E repainted all twenty boards at 3200×1800 and
they are in the game, so the upscale described above is history. What follows is
kept as the measurement that produced the request, and the three boards that were
worst before it landed:

| file | size before 18E | note |
|---|---|---|
| `flooded_gate.jpg` | 800×437 | a quarter of the roster norm; soft already in flat |
| `shibuya_night.webp` | 1200×675 | below the 1600 norm, on the busiest board — now `shibuya_night.jpg` |
| `curse_maw.jpg` | 1920×1640 | 1.17 aspect, not 16:9 — cropped hard, and 3d cropped it further |

The originals are kept at `assets/backgrounds/flat/` — see below.

**A board ships two plates now, one per camera.** 18E delivered the resolution
the measurement above asked for, but each plate was drawn fresh from the board's
brief rather than from the painting it replaced, so twenty scenes were
re-invented alongside being enlarged. Flat mode felt that most: it shows a whole
plate, and the outer ring 18E added was composed as camera headroom for the 3D
crop rather than as picture, so the boards read sparse and dim. So the pre-18E
paintings moved from `assets/reference/backgrounds_previous/` into
`assets/backgrounds/flat/` and the flat camera draws them again;
`backgroundFile()` in `src/stages.js` picks the plate and `src/assets.js`
fetches only the one the running camera wants (the mode is settled in `init()`
before any asset group is requested, so there is no double download and no
switch at runtime). 3d mode keeps the wide plates. Round **20B** in
[asset-requests.md](asset-requests.md) then replaces those wide plates with
extensions *of these same paintings* — 30% a side, so the 49.4% crop lands on
79% of the original picture — which is the version of 18E that should have been
asked for.

**What NOT to worry about.** Several boards are painted with a strong
one-point perspective (`crosswalk_rush`, `lantern_corridor` both recede to
a vanishing point). A painted vanishing point on a flat plane cannot
respond to a real camera, which sounds like it should fight the 3D — but
at ±0.88° of yaw it never gets the chance. It is visible only in drama
shots, and briefly.

**Summary:** ask for *bigger* paintings, not *layered* ones — and if you
want more depth than that, spend it on near-field garnish, where the
geometry actually rewards it.

## 11. Composing with the render backends *(built)*

`?render=` and `?camera=` are orthogonal: the first decides how a CHARACTER
becomes pixels, the second decides the stage and lens they exist in. They are
also the two features most likely to be set together, and for a while doing so
drew **no fighter at all** — the camera asked the render backend for a pose,
got an opaque model token (`r3d:idle@0.5`) it could not turn into a texture,
and skipped the quad. Neither side was wrong; no test set both flags.

The fix is not "make the camera handle tokens". A token is opaque by contract,
and flattening every backend into one representation would throw away exactly
what each is for. Instead a backend may declare **how it presents as
geometry**, via an optional `scene3d` adapter on its registry entry
(`sceneAdapter()` in `src/render_backend.js`):

| `?render=` | adapter | what the camera puts in the scene | why that is native |
|---|---|---|---|
| `sprite` | *(none)* | a textured quad of the sprite frame | a sprite is a drawing; a card is all it can be |
| `billboard` | `kind: "texture"` | a card wearing the **posed-model** texture | the backend's whole identity is "pose a rig, cache the texture, draw it flat" — a billboard in a 3D scene is a card |
| `3d` | `kind: "object"` | the **real rig**, added to this scene | the fighter already IS live rigged geometry; rendering it to an offscreen texture to paste a flat card into a 3D scene would discard the point of the backend |

The third row is the one worth the work. In-scene, the model gets real
perspective and foreshortening from the actual viewing angle instead of the
fixed ¾ offscreen camera, real depth against the extruded platforms
(occlusion out of the depth buffer, not a painter's sort), and the
micro-parallax dial **retires** — it exists only to fake, when blitting flat,
what a moving camera does for free.

Four things that design had to solve, three of them in
`src/camera3d/models.js`:

- **The sim group cannot hold a model.** Its transform is `(S, -S, 1)`, and a
  negative Y scale mirrors geometry and inverts its winding. Cards do not
  care. So the model group sits in world space and maps sim coordinates by
  hand, exactly as `makeSimGroup` does.
- **This scene has no lights** — everything else in it is unlit textured
  quads, and toon materials with no light have no terminator at all. The
  model layer carries its own rig, coloured from the same stage-tint
  derivation the flat path lights with (`stageLightTint()`), so a fighter is
  not lit two different ways depending on a URL flag.
- **One rig object per character, but two fighters can share a character.**
  The flat path poses one object and renders it to a texture, so two Gojos
  take turns; in a live scene they cannot. The loader hands out skeleton-aware
  **instances** keyed by fighter id, sharing the clips (read-only keyframe
  data that binds by bone name).
- **The floor is not world y = 0.** The pose pipeline's two ground solvers —
  `standOnGround` (drop the body until its feet reach the floor) and
  `plantFeet` (push a sunk foot back up) — read a foot's WORLD y and compared
  it against zero. That is the floor only while the rig stands at the origin,
  which is exactly how the offscreen blit poses it and never how this scene
  does: here the root is at the platform's own height. A fighter on a raised
  platform therefore read as standing metres in the air and the correction
  hauled them down by its whole ±0.6 m clamp — feet through the deck on every
  platform except the main one, which sits at world y = 0 and so looked fine.
  Both solvers now measure in the ROOT's frame (`groundOffset({ root })`),
  which is where the answer belongs anyway: `node.position.y` is local to the
  root, and so is the floor the fighter stands on. Guarded by
  `tools/smoke_ground3d.mjs`, on two boards — one whose main platform sits at
  world y = 0 and one terraced entirely below it, because the sign of the
  error is what made the bug look like "every platform but the bottom one".

Engine motion stays `motion.js`'s in every mode — lean, squash, tumble and
offsets are read there and applied to the object instead of to a canvas
transform, so game feel does not change with the camera flag.

Fallthrough stays per character: a fighter with no model draws as a card in
the same shot as one with, so a half-delivered roster mixes freely.

**Verification:** `tools/smoke_camera_render.mjs` asserts each combination
draws bodies by its own mechanism (`models`, `posedCards`, `quads`), not
merely that something appeared — every path ends in a fighter-shaped thing on
screen, so a pixel probe cannot tell which one produced it, and "it quietly
fell back to sprites" is precisely the failure being tested for.
`tools/smoke_ground3d.mjs` adds the other half a body needs once it is real
geometry: that it stands ON the platform rather than through it, measured off
the lowest FOOT BONE. Not a `Box3` — the AABB of a `SkinnedMesh` is its bind
pose through the root transform, nowhere near the posed feet, and believing it
hid this bug from the first probe written to find it.
